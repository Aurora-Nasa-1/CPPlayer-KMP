# 国际化（i18n）

> 文案接口树、语言策略、新增文案流程、九类坑与迁移状态。
> 目标：完整支持简体中文与英文，加语言不改架构。
> 事实源 `app/src/commonMain/kotlin/cp/player/app/i18n/`

## 1. 方案

| 项 | 选择 |
|---|---|
| 文案定义 | `i18n/CpStrings.kt`（接口，按区域分组） |
| 实现 | `CpStringsZh.kt`（兜底）、`CpStringsEn.kt` |
| 组合侧取值 | `val s = cpStrings()`（`@Composable @ReadOnlyComposable`） |
| 非组合取值 | `CpStrings.zh` / `CpStrings.en` / `CpStrings.of(lang)` |
| 注入 | `ProvideCpStrings(language) { … }`，全树只调一次（在 `AppTheme` 里） |
| 持久化 | `AppModel.appLanguageFlow` → `SettingsStorage["app_language"]` |

## 2. 为什么不用官方 compose-resources

选型时先做的是官方方案（`composeResources/values*/strings.xml` + `Res.string.*`），在 1.12.1 上做不到应用内切换语言，已回滚。

依据（上游 `v1.12.1` `components/resources/.../ResourceEnvironment.kt`）：

| 声明 | 可见性 |
|---|---|
| `class ResourceEnvironment internal constructor(...)` | 构造 `internal` |
| `interface ComposeEnvironment` | `internal` |
| `val LocalComposeEnvironment` | `internal` |
| `expect fun getSystemEnvironment()` | `internal` |
| `fun getSystemResourceEnvironment()` | 唯一 public，只能取系统值 |

所有自定义 locale 的入口都是 `internal`。

判可见性的坑：`javap` 会把它们显示成 `public class` / `public final`，那是 JVM 字节码层面的可见性，Kotlin 元数据里仍是 `internal`，Kotlin 侧引用直接 `unresolved reference`。核实库 API 的 Kotlin 可见性不能只看 `javap`，还要看 `@Metadata` 或上游源码。

`LocalComposeEnvironment` 被标 `internal` 多半是上游未定稿；真要换回官方方案，先重新核实这一条。

## 3. 为什么自建更合适

本仓库约一半文案不在组合上下文里：

| 场景 | 例子 |
|---|---|
| 事件通知 | `UiEvents.notify(...)`（Toast / 弹窗文案） |
| ScreenModel | 拼好的提示语 |
| 路由参数 | 塞进 Voyager 返回栈的 Screen 构造参数（如 `StartupScreen("正在初始化后端…")`） |

`stringResource()` 在这些地方根本调不了（要求组合作用域），`CpStrings` 是普通对象，哪儿都能读。

两份实现实现同一个接口 ⇒ 漏一条编译不过。这比「XML 缺 key 静默回落到另一种语言」可靠，后者要另写脚本查。

## 4. 语言策略

`AppLanguage`（`i18n/AppLanguage.kt`）三个取值，不是三种语言。

| 取值 | `storageKey` | 语义 |
|---|---|---|
| `SYSTEM` | `system` | 运行时读 Compose `Locale.current`，命中英文才用英文，其余一律中文 |
| `ZH_HANS` | `zh-Hans` | 强制简体中文 |
| `ENGLISH` | `en` | 强制英文 |

| 规则 | 内容 |
|---|---|
| 兜底语言 | 中文：用户群以中文为主，缺翻译时回落到看得懂的语言更可用；要改就动 `CpStrings.of` 里那一个 `else` |
| `storageKey` 不用枚举 `name` | 重命名枚举成员会让老用户的持久化值静默失效（用户会看到「我明明选了英文」） |
| 未知 key | `ofStorageKey` 匹配 `storageKey`，无法识别回落 `SYSTEM`；宁可回到跟随系统，也别让偏好项变成 crash 源 |
| `AppLanguage.tag` | 只用于持久化与调试输出；文案取值走 `CpStrings.of`，不要在那里造第二份解析 |

## 6. 加 / 改文案

### 6.1 三种调用形态

```kotlin
// ① Composable 里（最常见）
val s = cpStrings()
Text(s.settings.screenTitle)

// ② 需要在 Composable 之外构造数据（顶层函数、ScreenModel、事件回调）
//    传「取值函数」而不是「算好的字符串」，语言切换时仍会重新求值
val entries = settingsEntries()          // 里面存的是 titleOf: (CpStrings) -> String
entries.forEach { Text(it.titleOf(s)) }

// ③ 没有组合上下文、且本来就不该随语言变（日志、上报、错误码）
logger.warn(CpStrings.zh.settings.screenTitle)
```

不要在 `SettingsRegistry` 这类非组合顶层函数里调 `cpStrings()`：它是 `@Composable`，非组合上下文调用直接编译失败。这也是 `SettingsEntry` 存 `titleOf(strings)` 而不是 `StringResource` / `String` 的原因：存键或存函数能跟随语言切换，存算好的 `String` 不能。

### 6.2 步骤

| 步骤 | 动作 |
|---|---|
| 1 | 在 `CpStrings.kt` 找到合适分组加成员；没有就新建分组 |
| 2 | `CpStringsZh` / `CpStringsEn` 各写一份；漏了编译不过 |
| 3 | 调用点读 `cpStrings()` |
| 4 | 出图核对版式 |

| 约定 | 内容 |
|---|---|
| 标题 + 副标题 | 用 `CpTextPair`，别开两个平行的 `xxxTitle` / `xxxSubtitle` |
| 带数字 / 名字 | 写成函数，如 `fun downloadedMusicSummary(count: Int, bytes: String): String`；中英语序不同（`128 首 · 共 3.4 GB` vs `128 tracks · 3.4 GB`），调用方拼接就永远译不了 |
| 顺带检查 | 喂文案的枚举（见 7.1）与「这一片」的其他文件（见 7.2） |

## 7. 九类坑

### 7.1 喂文案的枚举

有一类东西自己没有字面量，却把中文喂给界面：枚举的 `displayName()` / `label` / `title`。漏掉它们的后果是英文界面里并排出现中英（`Follow system / 浅色 / 深色`），而且编译不报错、单测不红，只有出图看得见。

已处理的四处：

| 位置 | 原形态 | 改成 |
|---|---|---|
| `ThemeMode.displayName()` | 无参扩展 | `displayName(strings)` |
| `ColorSource.displayName()` / `description()` | 无参扩展 | 收 `CpStrings` |
| `ShortcutCategory.title` / `ShortcutAction.label` + `hint` | 枚举构造参数里的 `String` | `titleOf/labelOf/hintOf: (CpStrings) -> String` |
| `ShortcutKey.label` | 枚举构造参数 | 拆成语言无关的 `label` + `labelOf(strings)` |

判据：任何 `fun xxxDisplayName()` 或枚举里的 `val label: String` 出现在 UI 上，就要问「它读得到语言吗」。读不到就是隐患 —— 枚举构造参数在类加载时求值，那一刻还没有语言状态。

`ShortcutKey` 的拆法值得记：不要把三个中文键名留在 `label` 里再在别处特判。现在 `label` 只放语言无关部分（`F5` / `←` / `A`），带 CJK 的三个（空格 / 回车 / 退格）由 `labelOf` 查文案层，`isNotBlank()` 一行分流。

### 7.2 页面迁完 ≠ 这一片迁完

迁完一个页面文件，不等于迁完它那一「片」。页面只是链路最后一环，它点开的弹窗、走的共享组件、下游 model 里的提示语都可能是独立文件里的中文。

批次 1 收尾按页面文件复测，四个文件全是 0 残留，但同批补的两处正是漏网：

| 漏网处 | 为什么容易漏 | 归到哪组 |
|---|---|---|
| `ui/component/SleepTimerDialog.kt` | 三处共用（设置页 / `PlayerMoreBottomSheet` / 玩家界面）的弹窗，页面上只是一行 `SettingsClickItem` | `playback.timerDialog*` |
| `ui/component/CpConfirmDialog.kt` | 全应用统一确认框，14 个调用点跨 9 页 | `common.confirm` / `common.dismiss` |

复测口径按「这一片」而不是「那个文件」：迁完某页后 grep 它引用到的组件 / 弹窗 / model，看各自文件里的 CJK 字面量。更省事的做法是把「页面 + 它依赖的组件」当一个单元排期。

共用组件优先迁：`SleepTimerDialog` 一处迁完，三个入口同时生效。

### 7.3 状态与文案耦死

7.1 那一类至少能靠出图发现；状态与文案耦死连出图都发现不了 —— 界面完全正常，只是行为错了。

```kotlin
// 旧版：AppModel 发成品中文串
_handoffMessage.value = "转移失败：${reason} —— 本机继续播放"

// UI 靠字面前缀判断成败，决定用不用错误色
color = if (msg.startsWith("转移失败")) error else onSurfaceVariant
```

| 后果 | 表现 |
|---|---|
| 改文案 → 判断静默失配 | 把「转移失败」换成别的说法，失败提示变成普通信息色 |
| 换语言 → 判断恒为 false | 英文界面没有那个中文串，所有失败显示成「一切正常」的灰色 |
| 单测测不出来 | 断言的是文案长什么样，没人断言「配色判据还成立」 |

正确解法：状态流不带文案。

```kotlin
sealed interface HandoffState {
    data class Failed(val reason: String?) : HandoffState
    val failed: Boolean get() = this is Failed || this is TakeOverFailed || this is NoTrack
    fun textOf(strings: CpStrings): String = when (this) { … }
}
```

成败看 `failed`（类型），组文案走 `textOf(strings)`（渲染那一刻）。两个消费点（`StandbySettingsScreen` / `DevicePickerSheet`）都改读 `handoffStateFlow`。

判据：`startsWith("…")` / `contains("…")` / `== "某句中文"` 出现在决定行为（配色、是否重试、是否弹窗）的地方，就是这个坑。

配套守卫 `i18n/HandoffStateTest`（5 条）：逐个分支钉住 `failed` 分类、两种语言都非空、中英文案必须不同、设备名 / 原因真的进了句子、空原因回落到兜底。

### 7.4 枚举携带文案 ⇒ 单测要改签名

把 `String` 换成 `(CpStrings) -> String` 会改掉既有测试的调用形态：`ShortcutBindingTest` / `SongCacheUiStateTest` 原本直接调 `action.label`、`qualityLabel("standard")`，迁移后必须显式传语言。

顺手把断言扩成两种语言：原来只测中文，「英文下这些词一个没翻」照样全绿。

### 7.5 带参文案是测试盲区

`fun deleted(name, freed)` 这类带参文案不会被 `collectStrings` 的反射遍历碰到（它只认无参成员 = Kotlin 的 `val`）。实现里漏用一个参数，编译通过，界面上是一句残缺的话。

`CpStringsTest` 因此补了 `collectParameterizedStrings`：给每个参数位发哨兵实参（字符串位 `<P0>` / `<P1>`…，数值位给真数字 `12345`），再断言输出里能找到每个哨兵，顺带咬住「把数量写死成常量」。四处设计取舍：

| 取舍 | 理由 |
|---|---|
| `labelOf` 这类查表函数的 `else` 故意原样返回入参 | 未知档位显示标识符好过空白 ⇒ 输出等于哨兵时跳过断言 |
| 数值哨兵用真数字 | 字符串哨兵也能进模板，但真数字才能发现 `count` 根本没被用 |
| 数值哨兵按「3 位数字窗口」匹配 | 参数参与算术是合法需求：`"${minutes + 1} 分钟后"` 在英文侧同样成立；整串匹配会误判。3 位是刻意的：更短会让 `"共 3 条"` 里的 `3` 蒙混，更长则 `+1` 匹配不上 |
| 另加 `usedIn` 正反例自检 | 放宽判定会漏报；没有它，某天有人把 `usedIn` 简化成 `isNotEmpty()`，整个哨兵机制会静默退化成永真而仍然全绿 |

### 7.6 文案里不许留 Markdown

`SettingsNote` / `Text` 不解析 Markdown。原文案里的 `**加粗**` 会把星号原样显示在界面上。实锤：局域网页的自动同步警告，中英两条都写着 `**听歌记录**` / `**and write**`，在粉色警告背景上飘着四个星号，只有出图能看出来。

修法：强调语义改用引号（中文「」/ 英文 `""`），并加守卫 `CpStringsTest.no string carries markdown or emphasis markers`：遍历两棵树的全部无参成员 + 带参函数输出，禁止 `**` 与反引号。

### 7.7 非 composable 上下文拿 `CpStrings` 的三种形态

| 形态 | 例子 | 做法 |
|---|---|---|
| 顶层 `val` | `private val LibraryFilters = listOf(FilterTab("歌单", …))` | 改成 `fun libraryFilters(s: CpStrings)`；顶层属性在类加载时求值，那时没有语言状态 ⇒ 标签页永远一种语言 |
| 非 composable 函数 | `validateStreamPort(text)`、`askDeleteOrUnsubscribe(…)` | 加 `s: CpStrings` 参数，由组合内的调用方传 |
| `LazyListScope` 扩展 | `LazyListScope.playlistsSection(…)` | 同上；它和 `LazyScrollColumn` 的 content lambda 都不是 `@Composable`，状态与文案都由 `@Composable` 宿主当参数传进来 |

顶层 `val` 这一类编译不报错、单测不红，只是标签永远不变；出图也看不出（两种语言下它显示同一种）。判据：看到顶层 `private val X = listOf(... 文案 ...)` 就该警惕。

### 7.8 函数入参与 Compose 作用域

| 调用点 | 声明方式 |
|---|---|
| 全在 Compose 上下文中 | 标记 `@Composable`，函数内部用 `cpStrings()` |
| 含非 Compose 上下文（后台模型、普通计算函数） | 显式传入 `s: CpStrings` |

### 7.9 平台层文案

`platform/` 与 `shortcut/Shortcut.kt` 里的中文字面量不全是用户可见文案，混着日志、调试输出与持久化默认值。

| 类型 | 处理 |
|---|---|
| 写进日志 / 异常信息 | 不必翻译 |
| 出现在 UI（窗口标题、托盘菜单、快捷键编辑器） | 要翻译 |
| 快捷键持久化标识 | 只译显示名，绝不译 id / 持久化键；改键名会让老用户保存的绑定全部失效 |

`shortcut/Shortcut.kt` 原属批次 7，已随批次 1 迁完：它喂的是快捷键页文案，拆开做只会让那一页半中半英。

## 9. 已知边界

| 边界 | 说明 |
|---|---|
| 即时切换范围 | 只覆盖读过 `cpStrings()` 的地方；在组合外就把文案固化进状态的地方（已 push 的 Screen、算好的字符串放进 ViewModel）不会随切换更新，要改成传函数 / key |
| `object` 与枚举读不到语言 | `AppModel` 是 `object`、枚举构造参数在类加载时求值；出路只有两条：① 只存标识（`qualityLevels` 只存 level），显示名查文案层；② 存取值函数 `(CpStrings) -> String` |
| 顶层 `val` | 同类坑且更难发现，见 7.7 |
| 协程里的通知 | 由调用方传 `strings`（照 `SongCacheModel.remove(entry, strings)`），IO 协程读不到 CompositionLocal，传进来还保证用点击那一刻的语言 |
| 状态流 | 不带文案，见 7.3 |
| 协议层 message | `HandoffResult.message`、`PushResult.message` 是对端给的原始串（可能还是对方语言），原样透出；冒充成本地翻译反而误导。彻底解决要改成协议级错误码（core 改动、影响两端兼容） |
| 语言入口 | 只有设置 → 语言一处；主界面直接切换尚未做 |
| 加第三种语言 | 加 `AppLanguage` 成员 + `CpStringsXxx` 实现 + `CpStrings.of` 里加分支，架构不变 |
