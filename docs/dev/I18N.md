# 多语言（i18n）实施说明

> 目标：**完整支持简体中文与英文**，且后续加语言不需要改架构。
>
> 本文既是「现在怎么跑」的说明，也是剩余 ~1600 条文案的迁移工单。
> 每批迁移完请更新 §7 的进度表，方便他人接手。

## 1. 方案：自建文案接口树（**不是** compose-resources）

| 项 | 选择 |
| --- | --- |
| 文案定义 | `i18n/CpStrings.kt`（**接口**，按区域分组） |
| 两份实现 | `i18n/CpStringsZh.kt`（兜底）/ `i18n/CpStringsEn.kt` |
| 组合侧取值 | `val s = cpStrings()`（`@Composable @ReadOnlyComposable`） |
| 非组合取值 | `CpStrings.zh` / `CpStrings.en` / `CpStrings.of(lang)` |
| 注入宿主 | `ProvideCpStrings(language) { … }`，全树**只调一次**（在 `AppTheme` 里） |
| 持久化 | `AppModel.appLanguageFlow` → `SettingsStorage["app_language"]` |

### 1.1 为什么否掉官方 `compose-resources`

选型时先做的是官方方案（`composeResources/values*/strings.xml` + `Res.string.*`），
**在 1.12.1 上做不到应用内切换语言**，已回滚。依据（上游 `v1.12.1`
`components/resources/library/src/commonMain/kotlin/org/jetbrains/compose/resources/ResourceEnvironment.kt`）：

```kotlin
class ResourceEnvironment internal constructor(...)   // 构造 internal
internal interface ComposeEnvironment
internal val LocalComposeEnvironment = staticCompositionLocalOf { … }
internal expect fun getSystemEnvironment()
fun getSystemResourceEnvironment(): ResourceEnvironment   // 唯一 public，只能取「系统」值
```

**所有自定义 locale 的入口都是 `internal`。**

> ⚠️ **判可见性的坑**：`javap` 会把这些显示成 `public class` / `public final`——
> 那是 **JVM 字节码层面**的可见性，**Kotlin 元数据里仍是 `internal`**，
> Kotlin 侧引用会直接 `unresolved reference`。核实库 API 的 Kotlin 可见性
> **不能只看 `javap`**，还要看 `@Metadata` 或上游源码。

顺带一提，`LocalComposeEnvironment` 被标 `internal` 多半是上游尚未定稿的 API，
未来版本可能开放 —— 真要换回官方方案，先重新核实这一条。

### 1.2 为什么自建反而更合适本仓库

本仓库**约一半文案不在组合上下文里**：

- `UiEvents.notify(...)`（Toast / 弹窗文案）
- ScreenModel 里拼好的提示语
- 塞进 Voyager 返回栈的 Screen 构造参数（如 `StartupScreen("正在初始化后端…")`）

`stringResource()` 在这些地方**根本调不了**（它要求组合作用域），而
`CpStrings` 是个普通对象，**哪儿都能读**。

而且两份实现实现同一个接口 ⇒ **漏一条编译不过**。
这比「XML 里缺 key 静默回落到另一种语言」可靠得多（那种要另写脚本查）。

## 2. 语言策略

`AppLanguage`（`i18n/AppLanguage.kt`）三个取值 —— 注意**不是三种语言**：

| 取值 | `storageKey` | 语义 |
| --- | --- | --- |
| `SYSTEM` | `system` | 运行时读 Compose `Locale.current`，**命中英文才用英文，其余一律中文** |
| `ZH_HANS` | `zh-Hans` | 强制简体中文 |
| `ENGLISH` | `en` | 强制英文 |

- **中文是兜底语言**（用户群以中文为主，缺翻译时回落到看得懂的语言比回落到另一种外语更可用）。
  要改兜底语言：改 `CpStrings.of` 里那**一个** `else` 分支。
- `storageKey` 刻意**不用枚举 `name`**：重命名枚举成员会让老用户的持久化值静默失效
  （用户会发现「我明明选了英文」）。`ofStorageKey` 匹配 `storageKey`，无法识别时回落 `SYSTEM`
  —— 宁可在语言上回到跟随系统，也别让一个偏好项变成 crash 源。
- `AppLanguage.tag` **目前只用于持久化与调试输出**，文案取值不经过它（走 `CpStrings.of`）。
  别在那里再造第二份解析逻辑。

## 3. 已接入的部分

- `i18n/AppLanguage.kt` —— 语言枚举 + `displayName()` / `displayNote()`。
  ⚠️ 选项显示名**刻意不**做成 `LanguageStrings` 的三个成员：那是把「枚举有几个取值」
  和「每个取值叫什么」拆到两处维护，加一种语言要改两个地方。
- `i18n/CpStrings.kt` —— 文案接口树 + `cpStrings()` / `ProvideCpStrings()`。
  `LocalCpStrings` 默认值给中文，让**未接 `ProvideCpStrings` 的场景**
  （预览、单测直接调某个 composable）也能渲染，而不是抛「composition local 未赋值」。
- `AppModel` —— `appLanguageFlow` + `setAppLanguage()`，走既有 `SettingsStorage`。
- `App.kt` —— 在 `AppTheme` 里订阅并罩住整棵树（含 Navigator 与桌面自绘标题栏）。
  **必须挂在 `AppTheme`**：它是全树唯一的主题宿主，才能保证切换后立即生效、不漏分支。
- `ui/screen/SettingsRegistry.kt` —— 存 `titleOf(strings)` / `subtitleOf(strings)` 取值函数
  （**不存** `StringResource`，理由见 §4.1）。
- `ui/screen/LanguageSettingsScreen.kt` —— 三选一的语言页，选后立即生效并返回。

## 4. 加 / 改文案的步骤

### 4.1 三种调用形态

```kotlin
// ① Composable 里（最常见）
val s = cpStrings()
Text(s.settings.screenTitle)

// ② 需要在 Composable 之外构造数据（顶层函数、ScreenModel、事件回调）
//    —— 传「取值函数」而不是「算好的字符串」，这样语言切换时仍会重新求值
val entries = settingsEntries()          // 里面存的是 titleOf: (CpStrings) -> String
entries.forEach { Text(it.titleOf(s)) }

// ③ 完全没有组合上下文、且本来就不该随语言变（写日志、上报、错误码）
//    —— 直接用具体实例，别读 LocalCpStrings
logger.warn(CpStrings.zh.settings.screenTitle)
```

> ⚠️ **别在 `SettingsRegistry` 这类非组合顶层函数里调 `cpStrings()`** ——
> 它是 `@Composable`，在非组合上下文调用会直接编译失败。
> 这也是 `SettingsEntry` 存 `titleOf(strings)` 而不是 `StringResource` / `String` 的原因：
> 存键或存函数都能跟随语言切换，**存算好的 `String` 则不能**。

### 4.2 加一条文案

1. 在 `CpStrings.kt` 里找到合适的分组接口加成员（没有合适分组就新建一个）；
2. `CpStringsZh` / `CpStringsEn` **各写一份** —— 漏了编译不过；
3. 调用点读 `cpStrings()`；
4. **出图核对**（§4.3）。

「标题 + 副标题」成对出现（设置入口几乎都是这个形状）用 `CpTextPair`，
别开两个平行的 `xxxTitle` / `xxxSubtitle`。

### 4.3 改完必须出图核对版式

**编译和单测都量不到「字撑破了行」「副标题被截成半句」。**
中文文案普遍比英文短一大截：`通用` → `General`、`连接与集成` →
`Connections & Integrations`、`局域网设备` 那条副标题从 30 字符涨到 110 字符。

跑：

```
./gradlew :app:desktopTest --tests "cp.player.app.ui.preview.SettingsI18nPreviewTest"
```

出图落在 `app/build-verify/preview/i18n-*.png`（宽屏 1200 / 窄屏 480 / 语言页 520）。
**窄屏那张是英文最容易翻车的地方**，必须看。

> 已用出图抓到过编译和单测都发现不了的问题：中文界面里混进了未翻译的英文。
> （`optionEnglish = "English"` 那类是**有意的**，语言列表按语言自称显示是国际惯例，
> 与 Windows / macOS 语言列表一致 —— 代码里已加注释固化，别当漏译改掉。）

### 5.2 平台层文案要当心

`platform/` 与 `shortcut/Shortcut.kt` 里的中文字面量**不全是用户可见文案**，
混着日志、调试输出、以及**持久化用的默认值**。迁移时逐条判断：

- 写进日志 / 异常信息的 → **不必翻译**（开发者和用户都不读）。
- 出现在 UI（窗口标题、托盘菜单、快捷键编辑器）→ 要翻译。
- **快捷键的持久化标识**：只译显示名（`title`），**绝不译 id / 持久化键** ——
  改键名会让老用户保存的绑定全部失效。参见 `AGENTS.md` §快捷键三态持久化。

## 6. 已知边界

- **即时切换只覆盖读过 `cpStrings()` 的地方。** 在组合外就把文案固化进状态的地方
  （例如已 push 进返回栈的 Screen、已经算好的字符串放进 ViewModel）
  **不会**随切换更新。迁移这类代码时要改成传函数 / key。
- 语言页目前**只此一处**入口（设置 → 语言）。主界面直接切换的入口尚未做。
- 目前只两种语言。加第三种时：加 `AppLanguage` 成员 + `CpStringsXxx` 实现 +
  在 `CpStrings.of` 里加分支 —— 架构上不需要其他改动。
