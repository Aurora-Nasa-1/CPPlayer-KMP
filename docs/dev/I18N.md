# 多语言（i18n）实施说明

> 目标：**完整支持简体中文与英文**，且后续加语言不需要改架构。
>
> 本文既是「现在怎么跑」的说明，也是剩余文案的迁移工单。
> 每批迁移完请更新 §5 的进度表与 §5.1 的批次表，方便他人接手。

## 1. 方案：自建文案接口树（**不是** compose-resources）

| 项 | 选择 |
| --- | --- |
| 文案定义 | `i18n/CpStrings.kt`（**接口**，按区域分组） |
| 两份实现 | `i18n/CpStringsZh.kt`（兜底）/ `i18n/CpStringsEn.kt` |
| 组合侧取值 | `val s = cpStrings()`（`@Composable @ReadOnlyComposable`） |
| 非组合取值 | `CpStrings.zh` / `CpStrings.en` / `CpStrings.of(lang)` |
| 注入宿主 | `ProvideCpStrings(language) { … }`，全树**只调一次**（在 `AppTheme` 里） |
| 持久化 | `AppModel.appLanguageFlow` → `SettingsStorage["app_language"]` |

### 1.1 为什么否掉官方 `compose-resources`

选型时先做的是官方方案（`composeResources/values*/strings.xml` + `Res.string.*`），
**在 1.12.1 上做不到应用内切换语言**，已回滚。依据（上游 `v1.12.1`
`components/resources/library/src/commonMain/kotlin/org/jetbrains/compose/resources/ResourceEnvironment.kt`）：

```kotlin
class ResourceEnvironment internal constructor(...)   // 构造 internal
internal interface ComposeEnvironment
internal val LocalComposeEnvironment = staticCompositionLocalOf { … }
internal expect fun getSystemEnvironment()
fun getSystemResourceEnvironment(): ResourceEnvironment   // 唯一 public，只能取「系统」值
```

**所有自定义 locale 的入口都是 `internal`。**

> ⚠️ **判可见性的坑**：`javap` 会把这些显示成 `public class` / `public final`——
> 那是 **JVM 字节码层面**的可见性，**Kotlin 元数据里仍是 `internal`**，
> Kotlin 侧引用会直接 `unresolved reference`。核实库 API 的 Kotlin 可见性
> **不能只看 `javap`**，还要看 `@Metadata` 或上游源码。

顺带一提，`LocalComposeEnvironment` 被标 `internal` 多半是上游尚未定稿的 API，
未来版本可能开放 —— 真要换回官方方案，先重新核实这一条。

### 1.2 为什么自建反而更合适本仓库

本仓库**约一半文案不在组合上下文里**：

- `UiEvents.notify(...)`（Toast / 弹窗文案）
- ScreenModel 里拼好的提示语
- 塞进 Voyager 返回栈的 Screen 构造参数（如 `StartupScreen("正在初始化后端…")`）

`stringResource()` 在这些地方**根本调不了**（它要求组合作用域），而
`CpStrings` 是个普通对象，**哪儿都能读**。

而且两份实现实现同一个接口 ⇒ **漏一条编译不过**。
这比「XML 里缺 key 静默回落到另一种语言」可靠得多（那种要另写脚本查）。

## 2. 语言策略

`AppLanguage`（`i18n/AppLanguage.kt`）三个取值 —— 注意**不是三种语言**：

| 取值 | `storageKey` | 语义 |
| --- | --- | --- |
| `SYSTEM` | `system` | 运行时读 Compose `Locale.current`，**命中英文才用英文，其余一律中文** |
| `ZH_HANS` | `zh-Hans` | 强制简体中文 |
| `ENGLISH` | `en` | 强制英文 |

- **中文是兜底语言**（用户群以中文为主，缺翻译时回落到看得懂的语言比回落到另一种外语更可用）。
  要改兜底语言：改 `CpStrings.of` 里那**一个** `else` 分支。
- `storageKey` 刻意**不用枚举 `name`**：重命名枚举成员会让老用户的持久化值静默失效
  （用户会发现「我明明选了英文」）。`ofStorageKey` 匹配 `storageKey`，无法识别时回落 `SYSTEM`
  —— 宁可在语言上回到跟随系统，也别让一个偏好项变成 crash 源。
- `AppLanguage.tag` **目前只用于持久化与调试输出**，文案取值不经过它（走 `CpStrings.of`）。
  别在那里再造第二份解析逻辑。

## 3. 已接入的部分

- `i18n/AppLanguage.kt` —— 语言枚举 + `displayName()` / `displayNote()`。
  ⚠️ 选项显示名**刻意不**做成 `LanguageStrings` 的三个成员：那是把「枚举有几个取值」
  和「每个取值叫什么」拆到两处维护，加一种语言要改两个地方。
- `i18n/CpStrings.kt` —— 文案接口树 + `cpStrings()` / `ProvideCpStrings()`。
  `LocalCpStrings` 默认值给中文，让**未接 `ProvideCpStrings` 的场景**
  （预览、单测直接调某个 composable）也能渲染，而不是抛「composition local 未赋值」。
- `AppModel` —— `appLanguageFlow` + `setAppLanguage()`，走既有 `SettingsStorage`。
- `App.kt` —— 在 `AppTheme` 里订阅并罩住整棵树（含 Navigator 与桌面自绘标题栏）。
  **必须挂在 `AppTheme`**：它是全树唯一的主题宿主，才能保证切换后立即生效、不漏分支。
- `ui/screen/SettingsRegistry.kt` —— 存 `titleOf(strings)` / `subtitleOf(strings)` 取值函数
  （**不存** `StringResource`，理由见 §4.1）。
- `ui/screen/LanguageSettingsScreen.kt` —— 三选一的语言页，选后立即生效并返回。
- 设置子页 5 屏（`AppearanceSettingsScreen` / `StorageSettingsScreen` /
  `PlaybackSettingsScreen` / `ShortcutSettingsScreen` / `SongCacheScreen`）—— 批次 1。
- `ui/component/SettingsKit.kt` —— 组件库的共享文案（「应用 / 未保存 / 确认 / 取消」）
  归到 `CommonStrings`，一次改动十个页面跟着变。
- `ui/component/SleepTimerDialog.kt` —— **三处共用**的睡眠定时弹窗（设置页 / 播放页 /
  玩家界面），文案归到 `PlaybackStrings.timerDialog*`。改一处，三个入口同时生效。
- `ui/component/CpConfirmDialog.kt` —— 全应用统一确认框（14 个调用点跨 9 页），
  `confirmLabel` / `dismissLabel` 存 `null`、在弹窗里按当前语言兜底（理由见 §5.1）。
- 连接与集成 3 屏（`StreamOutputSettingsScreen` / `IntegrationSettingsScreen` /
  `StandbySettingsScreen`）+ `DevicePickerSheet` —— 批次 2。
  ⚠️ 顺带把 `AppModel.handoffMessageFlow` 重构为 `handoffStateFlow: StateFlow<HandoffState?>`，
  原因见 §5.5（**这不是 i18n 独有的问题**，是 bilingual UI 的通用坑）。

## 4. 加 / 改文案的步骤

### 4.1 三种调用形态

```kotlin
// ① Composable 里（最常见）
val s = cpStrings()
Text(s.settings.screenTitle)

// ② 需要在 Composable 之外构造数据（顶层函数、ScreenModel、事件回调）
//    —— 传「取值函数」而不是「算好的字符串」，这样语言切换时仍会重新求值
val entries = settingsEntries()          // 里面存的是 titleOf: (CpStrings) -> String
entries.forEach { Text(it.titleOf(s)) }

// ③ 完全没有组合上下文、且本来就不该随语言变（写日志、上报、错误码）
//    —— 直接用具体实例，别读 LocalCpStrings
logger.warn(CpStrings.zh.settings.screenTitle)
```

> ⚠️ **别在 `SettingsRegistry` 这类非组合顶层函数里调 `cpStrings()`** ——
> 它是 `@Composable`，在非组合上下文调用会直接编译失败。
> 这也是 `SettingsEntry` 存 `titleOf(strings)` 而不是 `StringResource` / `String` 的原因：
> 存键或存函数都能跟随语言切换，**存算好的 `String` 则不能**。

### 4.2 加一条文案

1. 在 `CpStrings.kt` 里找到合适的分组接口加成员（没有合适分组就新建一个）；
2. `CpStringsZh` / `CpStringsEn` **各写一份** —— 漏了编译不过；
3. 调用点读 `cpStrings()`；
4. **出图核对**（§4.3）。

「标题 + 副标题」成对出现（设置入口几乎都是这个形状）用 `CpTextPair`，
别开两个平行的 `xxxTitle` / `xxxSubtitle`。

**带数字 / 名字的句子要写成函数**，比如
`fun downloadedMusicSummary(count: Int, bytes: String): String`。
中英语序不同（`128 首 · 共 3.4 GB` vs `128 tracks · 3.4 GB`），
在调用方拼就永远译不了；而函数形态还能被守卫测试用哨兵实参咬住（§5.5）。

> ⚠️ 迁某一页时顺手查一遍**喂文案的枚举**（§5.3）：`displayName()` / `label` / `title`
> 这类东西自己没字面量却把中文送到界面上，漏了编译不报错、单测不红，**只有出图看得见**。
>
> ⚠️ 再往前一步查**这一片**（§5.4）：页面点开的弹窗、它走的共享组件，都可能是
> 独立文件里的中文。反过来，**共用组件优先迁** —— 一处改完多个入口同时生效。

### 4.3 改完必须出图核对版式

**编译和单测都量不到「字撑破了行」「副标题被截成半句」。**
中文文案普遍比英文短一大截：`通用` → `General`、`连接与集成` →
`Connections & Integrations`、`局域网设备` 那条副标题从 30 字符涨到 110 字符。

跑：

```
./gradlew :app:desktopTest --tests "cp.player.app.ui.preview.SettingsI18nPreviewTest"
```

出图落在 `app/build-verify/preview/i18n-*.png`（宽屏 1200 / 窄屏 480 / 语言页 520）。
**窄屏那张是英文最容易翻车的地方**，必须看。

> 已用出图抓到过编译和单测都发现不了的问题：中文界面里混进了未翻译的英文。
> （`optionEnglish = "English"` 那类是**有意的**，语言列表按语言自称显示是国际惯例，
> 与 Windows / macOS 语言列表一致 —— 代码里已加注释固化，别当漏译改掉。）

### 5.2 平台层文案要当心

`platform/` 与 `shortcut/Shortcut.kt` 里的中文字面量**不全是用户可见文案**，
混着日志、调试输出、以及**持久化用的默认值**。迁移时逐条判断：

- 写进日志 / 异常信息的 → **不必翻译**（开发者和用户都不读）。
- 出现在 UI（窗口标题、托盘菜单、快捷键编辑器）→ 要翻译。
- **快捷键的持久化标识**：只译显示名，**绝不译 id / 持久化键** ——
  改键名会让老用户保存的绑定全部失效。参见 `AGENTS.md` §快捷键三态持久化。

### 5.3 ⚠️ 别漏「喂文案的枚举」

**页面文案只是半条链。** 有一类东西自己没有字面量，却把中文「喂」给界面 ——
枚举的 `displayName()` / `label` / `title` 之类。漏掉它们的后果是
**英文界面里并排出现中英**（`Follow system / 浅色 / 深色`），而这种混排
**编译不会报错、单测也不会红，只有出图才看得见**。

已处理的四处（批次 1 一并做的）：

| 位置 | 原形态 | 改成 |
| --- | --- | --- |
| `ThemeMode.displayName()` | 无参扩展 | `displayName(strings)` |
| `ColorSource.displayName()/description()` | 无参扩展 | 收 `CpStrings` |
| `ShortcutCategory.title` / `ShortcutAction.label`+`hint` | 枚举构造参数里的 `String` | `titleOf/labelOf/hintOf: (CpStrings) -> String` |
| `ShortcutKey.label` | 枚举构造参数 | 拆成「语言无关的 `label`」+「`labelOf(strings)`」 |

**判据**：任何 `fun xxxDisplayName()` / 枚举里的 `val label: String` 出现在 UI 上，
就要问「它读得到语言吗」。读不到就是隐患 —— 枚举构造参数在类加载时求值，
那一刻还没有语言状态。

> `ShortcutKey` 的拆法值得记：**别把三个中文键名留在 `label` 里再在别处特判**。
> 现在 `label` 只放语言无关的部分（`F5` / `←` / `A`），带 CJK 的三个（空格 / 回车 / 退格）
> 由 `labelOf` 查文案层，`isNotBlank()` 一行搞定分流。加语言只动文案一处。

### 5.4 页面迁完了 ≠ 这一片迁完了

**迁完一个页面文件，不等于迁完了它那一「片」。** 页面只占链路的最后一环，
它点开的弹窗、它走的共享组件、它下游 model 里的提示语都可能是**独立文件**里的中文。

批次 1 收尾时按页面文件复测，四个文件全是 0 残留 —— 但同批补的两处正是漏网：

| 漏网处 | 为什么容易漏 | 归到哪组 |
| --- | --- | --- |
| `ui/component/SleepTimerDialog.kt` | **三处共用**（设置页 / 播放页 `PlayerMoreBottomSheet` / 玩家界面）的弹窗，页面上只是一行 `SettingsClickItem` | `playback.timerDialog*` |
| `ui/component/CpConfirmDialog.kt` | 全应用统一确认框，14 个调用点跨 9 个页面 | `common.confirm` / `common.dismiss` |

**复测口径要按「这一片」而不是「那个文件」**：迁完某页后，
grep 该页引用到的**组件 / 弹窗 / model**，看它们各自文件里的 CJK 字面量。
更省事的做法是：批次计划里把「页面 + 它依赖的组件」当一个单元一起排期，
别指望只盯页面文件能收干净。

> 附带一个好处：`SleepTimerDialog` 是三处共用 ⇒ 这一处迁完，**三个入口同时生效**。
> 共用组件的文案迁移性价比最高，优先做。

### 5.5 ⚠️⚠️ 状态与文案耦死 = 比「枚举携带文案」更严重

`§5.3` 那一类（枚举 / `object` 里的文案）至少还能靠「出图看到中英混排」发现。
**状态与文案耦死**这一类连出图都发现不了 —— 界面上完全正常，只是**行为**错了。

实锤（批次 2 的无缝转移）：

```kotlin
// 旧版：AppModel 发成品中文串
_handoffMessage.value = "转移失败：${reason} —— 本机继续播放"

// UI 靠字面前缀判断成败，决定用不用错误色
color = if (msg.startsWith("转移失败")) error else onSurfaceVariant
```

三个后果，**每一个都不会被编译器或常规测试发现**：

1. **改文案 → 判断静默失配**。把「转移失败」改成别的说法，失败提示就变成普通信息色。
2. **换语言 → 判断恒为 false**。英文界面下压根没有那个中文串 ⇒ 所有失败都显示成
   「一切正常」的灰色。
3. **单测测不出来**。测试断言的是「文案长什么样」，没人会想到去断言
   「配色判据还成立」。

**正确解法：状态流不带文案。**

```kotlin
sealed interface HandoffState {
    data class Failed(val reason: String?) : HandoffState
    val failed: Boolean get() = this is Failed || this is TakeOverFailed || this is NoTrack
    fun textOf(strings: CpStrings): String = when (this) { … }
}
```

判成败看 `failed`（类型），组文案走 `textOf(strings)`（渲染那一刻）。
两处消费点（`StandbySettingsScreen` / `DevicePickerSheet`）都改成读 `handoffStateFlow`。

**判据**：见到 `startsWith("…")` / `contains("…")` / `== "某句中文"` 出现在
**决定行为**（配色、是否重试、是否弹窗）的地方，就是这个坑。
`if (msg.startsWith("失败"))` 这种写法在中英双语文案下**必然**出错。

配套守卫 `i18n/HandoffStateTest`（5 条）：逐个分支钉住 `failed` 分类、
两种语言都非空、**中英文案必须不同**（防「英文实现粘了中文」这种偷懒）、
设备名/原因真的进了句子、空原因回落到兜底。

### 5.6 枚举携带文案 ⇒ 单元测试要跟着改签名

把 `String` 换成 `(CpStrings) -> String` 会**改掉既有测试的调用形态**。
`ShortcutBindingTest` / `SongCacheUiStateTest` 原本直接调 `action.label`、
`qualityLabel("standard")`，迁移后必须显式传语言。

**顺手把断言扩成两种语言**（本批已做）：原来只测中文，
「英文下这些词一个没翻」这类问题照样全绿。

### 5.7 带参数的文案是测试盲区

`fun deleted(name, freed)` 这类**带参**文案不会被 `collectStrings` 的反射遍历碰到
（它只认无参成员 = Kotlin 的 `val`）。实现里漏用一个参数，编译通过、界面上一句残缺的话。

`CpStringsTest` 因此补了 `collectParameterizedStrings`：给每个参数位发哨兵实参
（字符串位 `<P0>`/`<P1>`…，数值位给真数字 `12345`），再断言输出里能找到每个哨兵 ——
顺手也咬住「把数量写死成常量」。

三处刻意的设计取舍（都已写进代码注释）：

1. `labelOf` 这类查表函数的 `else` 分支**故意**原样返回入参
   （未知档位显示标识符本身好过空白）⇒ 输出等于哨兵时跳过断言。
2. 数值哨兵用真数字而非 `<Pn>` —— 字符串哨兵也能进模板，但真数字才能发现
   `count` 根本没被用。
3. ⚠️ **数值哨兵按「3 位数字窗口」匹配，不是整串匹配。** 因为**参数参与算术是合法需求**：
   睡眠定时的 `"${minutes + 1} 分钟后"`（向上取整到分钟）在英文侧同样成立。
   写整串匹配会把它误判成漏参 —— 实锤：这条规则第一次跑就红了
   （哨兵 `12345` vs 输出 `当前：12346 分钟后暂停`）。
   3 位窗口是刻意选的：更短会让 `"共 3 条"` 里那个 `3` 蒙混过关，更长则 `+1` 匹配不上。
4. 放宽判定的代价是「可能漏报」，所以另有一条**自检测试**给 `usedIn` 钉正反例
   （`共 3 条` / `时间未知` / 空输出 必须判为漏用）。**没有它，某天有人把
   `usedIn` 简化成 `isNotEmpty()`，整个哨兵机制会静默退化成永真而仍然「全绿」。**

### 5.8 ⚠️ 文案里不许留 Markdown 标记

`SettingsNote` / `Text` **不解析** Markdown。原文案里的 `**加粗**` 会把星号
**原样显示在界面上** —— 迁移时照搬是很自然的事（两份文案都带了就当是约定）。

实锤：局域网页的自动同步警告，中英两条都写着 `**听歌记录**` / `**and write**`，
在粉色警告背景上飘着四个星号。**只有出图能看出来**。

修法：强调语义改用引号（中文「」/ 英文 `""`），并加守卫
`CpStringsTest.no string carries markdown or emphasis markers` ——
遍历两棵树的**无参成员 + 带参函数输出**，禁止出现 `**` 与反引号。

> 这条守卫的价值在于：文案里出现 `**` 是个**纯文本层面**的问题，
> 不看渲染结果永远发现不了，而没人会主动去数星号。

### 5.9 非 composable 上下文拿 `CpStrings` 的三种形态

迁移时经常撞到「这里读不到 `cpStrings()`」。三种形态各有既定做法：

| 形态 | 例子 | 做法 |
| --- | --- | --- |
| **顶层 `val`** | `private val LibraryFilters = listOf(FilterTab("歌单", …))` | 改成 `fun libraryFilters(s: CpStrings)`。顶层属性在**类加载时**求值，那时没有语言状态 ⇒ 标签页永远一种语言 |
| **非 composable 函数** | `validateStreamPort(text)`、`askDeleteOrUnsubscribe(…)` | 加 `s: CpStrings` 参数，由组合内的调用方传 |
| **`LazyListScope` 扩展** | `LazyListScope.playlistsSection(…)` | 同上。注意它**不是** `@Composable`，且外层 `LazyScrollColumn` 的 content lambda 也不是（见 `AGENTS.md` 关于它的坑）—— 状态与文案都由 `@Composable` 宿主当参数传进来 |

⚠️ 顶层 `val` 这一类**编译不会报错、单测也不会红**，只是标签永远不变；
出图时也看不出「它没跟着语言变」（两种语言下它都显示同一种）——
**判据：看到顶层 `private val X = listOf(... 文案 ...)` 就该警惕。**

### 5.10 「加个 strings 参数」还是「标 @Composable」？

一批文案要传的**纯函数**（菜单项构建器、格式化器）有两种解法，选错会很痛：

| 做法 | 何时选 | 代价 |
| --- | --- | --- |
| **标 `@Composable`** | 调用点**全在组合上下文**里，且函数体只用到 `cpStrings()` | 函数变成 composable ⇒ 不能再从非组合上下文调用 |
| **加 `s: CpStrings` 参数** | 有调用点在非组合上下文（普通函数、`LazyListScope` 扩展、ScreenModel 方法） | 12 个调用点全要改 |

**本批踩了坑**：`SongContextMenu` 的 `songContextMenuItems` 先加 `s` 参数，
结果 12 个调用点里有 5 个在 `LazyListScope` 扩展内部（不是 `@Composable`）、
还有 `PlaylistDetailScreen` 存了一个 `(TrackSummary, Int) -> List<…>` 的
**普通函数类型变量**（存进 composable 参数传递）——为它改遍 6 个文件、往返十几次。
**最后回退重做：标 `@Composable`（12 个调用点零改动）+ 把那个变量改成
`@Composable (TrackSummary, Int) -> List<…>`**，一次通过。

**判据（下次直接照做）**：动手前先 `grep` 一下所有调用点，
- 全在 composable 里 → 标 `@Composable`（最省）；
- 有非 composable 的 → 加参数，**且要连带把「存函数类型的 val」改成
  `@Composable (…) -> …` 变体**（那些 val 也会变成调用点）。

**次要教训**：批量脚本改一批文件时，若某个文件的改动需要连带改其他文件
（这里是改函数签名 ⇒ 影响所有调用点），**要么一开始就选影响最小的方案，
要么直接回退**——在错误的方案上打补丁的边际收益是负的。

## 6. 已知边界

- **即时切换只覆盖读过 `cpStrings()` 的地方。** 在组合外就把文案固化进状态的地方
  （例如已 push 进返回栈的 Screen、已经算好的字符串放进 ViewModel）
  **不会**随切换更新。迁移这类代码时要改成传函数 / key。
- **`object` 与枚举里读不到语言。** `AppModel` 是 `object`、枚举构造参数在类加载时求值 ——
  那里存文案等于写死。两条出路：
  ① 只存**标识**（如 `qualityLevels` 只存 level），显示名查文案层；
  ② 存**取值函数**（`(CpStrings) -> String`），在组合处代入。判据见 §5.3。
- ⚠️ **顶层 `private val X = listOf(...文案...)` 是同一类坑，而且更难发现。**
  它在类加载时求值 ⇒ 标签永远一种语言；**编译不报错、单测不红、出图也看不出**
  （两种语言下它显示同一种）。判据：看到顶层 val 里装文案就警惕，改成 `fun f(s)`。
  另外两类非 composable 形态（非 composable 函数 / `LazyListScope` 扩展）见 §5.9。
- **协程里的通知要由调用方传 `strings`。** 照 `SongCacheModel.remove(entry, strings)` 写：
  IO 协程读不到 CompositionLocal，传进来还顺带保证用的是**点击那一刻**的语言。
- **状态流不要带文案。** UI 拿 `startsWith("失败")` 之类判断行为时，
  换语言就必然失配（§5.5）。发带类型的纯状态，文案在渲染时组。
- **协议层 / 跨设备传的 `message` 不参与本地化。** `HandoffResult.message`、
  `PushResult.message` 是**对端**给的原始串（可能还是对方语言），原样透出即可，
  冒充成「本地翻译过的文案」反而误导。要彻底解决得改成协议级错误码
  （core 改动、影响两端兼容），单列工单。
- 语言页目前**只此一处**入口（设置 → 语言）。主界面直接切换的入口尚未做。
- 目前只两种语言。加第三种时：加 `AppLanguage` 成员 + `CpStringsXxx` 实现 +
  在 `CpStrings.of` 里加分支 —— 架构上不需要其他改动。
